# PROMPT · 组合版（直接贴，不用拼）

> **什么时候用这个文件**
>
> 你已经知道要贴 `PROMPT-single-dialog-summary.md`（脱敏+提炼打底），
> 还想再叠加方向专属要求（逆向 / 漏洞）。
> 那直接用这里的组合版 —— **一整段复制，一个对话框搞定**。
>
> **选择规则**

| 你的对话是 | 贴哪个 |
|---|---|
| 漏洞扫描 / 渗透测试 / 复现漏洞 | [组合版 A · 漏洞方向](#组合版-a--漏洞方向) |
| 逆向 / 脱壳 / 找算法 / 还原协议 | [组合版 B · 逆向方向](#组合版-b--逆向方向) |
| 两者都有（挖洞时逆向了客户端） | [组合版 C · 混合](#组合版-c--混合双向交叉) |
| 不确定 / 只是想让对话变成笔记 | [组合版 D · 通用](#组合版-d--通用提炼) |
| 文章已经写好了，只要脱敏 | 变体 B（见 PROMPT-single-dialog-summary.md 末尾） |
| 想要完整的成文文章（多段对话合成一篇） | [PROMPTS.md](./PROMPTS.md) 里的方向提示词 |

> **不要混用的两种做法**：
> - ❌ 只贴方向提示词（PROMPTS.md 第 1/2 节）→ 会写出好文章，但**真实域名和 token 会留在里面**
> - ❌ 只贴脱敏提示词 → 脱敏到位，但**原理章节不够硬**（比如没要求画内存布局、没要求写推导链）
>
> **组合版把两个优势合并了。**

### 1. 原理章节必须画清楚"东西在哪"
逆向文章最容易写成"我点了几下 IDA"。必须让读者知道**代码/数据在文件或内存里的物理位置**：

| 位置 | 含义 | 怎么找到的 |
|---|---|---|
| 文件偏移 0x1234 | ... | ... |
| 虚拟地址 0x401000 | ... | ... |
| RVA +0x2345 | ... | ... |

并解释这三种地址的区别（文件偏移 / 虚拟地址 / RVA）—— 新手最常在这里迷路。
**明确标注每个数值是十进制还是十六进制。**

### 2. 关键函数必须给"证据"
不要只说"关键函数是 sub_401000"。要写：
- 它被谁调用（交叉引用）
- 参数和返回值是什么（从反编译结果读出来）
- 你**怎么确定**它是关键函数（调用频率？参数特征？返回后进了校验分支？）

### 3. 算法还原要写"推导链"——这是逆向文章的分水岭
不能直接给公式。必须写出**你怎么一步步推到那个公式的**：

    1. 观察：输入 "AAAA" → 输出 0x12345678
    2. 猜：是不是某种哈希？
    3. 验证：输入 "BBBB" → 输出 4 个字节同时变了 → 排除单字节哈希
    4. 拆函数：发现内部调用了 sub_X，其参数是前 8 字节
    5. 确认：sub_X 是标准 AES 的 S-BOX 查表
    6. 结论：写出最终算法

**"猜"和"验证"的过程不能删。**

### 4. 动态调试必须给"为什么在这里下断点"
新手最大的困惑是"为什么断在这个函数"。写清：
- 你观察到了什么现象（程序崩溃 / 界面变灰 / 网络请求发出）
- 你据此推断代码会在哪执行
- 你下了断点，看到了什么

### 5. 命令必须给"最小可运行版本"
例如 Frida：

    # 前置：设备已 root，frida-server 与客户端版本一致
    pip install frida-tools
    frida-ps -U                       # 确认能连上设备

    # 完整脚本
    frida -U -f com.example.app -l hook.js --no-pause

不要只给 `-l hook.js`（读者会卡在"hook.js 从哪来"）。
**给出的脚本必须完整可运行，不能有省略号。**

### 6. 必须说明工具的局限
常见坑要写出来：
- IDA 的 F5 反编译结果和真实逻辑不一致的情况
- 加壳样本在内存 dump 和静态反编译的差异
- 32 位和 64 位下 API 名称差异（`VirtualAlloc` vs `VirtualAllocEx`）
- 编译器优化造成的伪代码失真

### 7. 脱壳类额外要求
- 讲清楚**壳的原理**（它怎么改的控制流 / 怎么解的密）
- 讲清楚**为什么要在 OEP（原始入口点）dump**，过早或过晚会怎样
- 给出 dump 后的**验证方法**（能跑？能被静态工具正常识别？）

**主线必须是「漏洞」，不是「逆向」。**

逆向是为了**解释漏洞为什么存在、怎么被利用**，所以：
- 逆向细节只在**服务于漏洞可利用性**时才展开
- 读者读完要能回答："客户端在检查什么？这个检查能不能绕过？绕过之后影响什么？"
- 大段脱壳过程 / 反汇编逐行讲解 → 压缩成支撑结论的最小必要部分

如果这个漏洞最终**不在客户端**（比如逆向只是为了拿到接口协议，
真正的漏洞在服务端），就明确写成：
「逆向阶段的目标是 XXX（为了拿到 YYY），实际发现的漏洞在 ZZZ」

【第三部分 · 具体要求】
═══════════════════════════════════════════════════════════

### 1. 原理章节（混合类的核心）
必须画清楚这条链：

    客户端做了什么检查（具体哪个函数、什么判断）
        ↓
    这个检查为什么可以被绕过（绕过手段 + 为什么有效）
        ↓
    绕过后能做什么（调用了什么接口 / 拿到什么数据 / 影响什么）

### 2. 逆向证据要给足
- 关键函数名 + 偏移量 + 伪代码片段
- 交叉引用（谁调用它）
- **你怎么确定这个函数是校验逻辑**（判定依据）
- 算法还原给推导链，不要直接给结论

### 3. 最小复现
两种都写：
- **客户端侧**：怎么构造能通过/绕过校验的请求或数据（用 `TARGET` 占位）
- **服务端侧**：完整原始 HTTP 报文 + 预期 vs 实际响应差异

### 4. 影响面与严重度
CVSS 向量 + **哪些情况下不成立**（前置条件，比如需要特定设备、版本、账号类型）

### 5. 修复建议
- 客户端侧：校验逻辑该怎么改（移到服务端 / 加签名 / 完整性校验）
- 服务端侧：接口该怎么加校验
- **强调根本原则：客户端校验只是体验优化，不能当安全边界**

### 6. 怎么找到的
两段都要有：
- 逆向侧：怎么发现这个校验存在（strings / 动态观察 / 抓包异常）
- 挖洞侧：怎么知道这个方向值得挖（什么信号）

```
这次对话里有"真实的漏洞发现"吗？
│
├─ 有，而且是逆向出来的（客户端校验可绕过）
│    └─▶ 组合版 C（混合）
│
├─ 有，是服务端/接口/配置类的
│    └─▶ 组合版 A（漏洞方向）
│
├─ 没有漏洞，纯技术分析（脱壳、还原算法、还原协议）

**再叠加一层判断**：

```

│

└─ 否（已经是成文文章了）→ 变体 B（只做脱敏，不改内容）

## 三种容易搞混的写法

| 你想要 | 用什么 | 别用什么 |
|---|---|---|
| 一篇能公开发布的完整技术文章 | 组合版 A/B/C/D | 单贴方向提示词（会漏脱敏） |
| 只留"下次怎么办" | 单对话摘要的**变体 A** | 组合版（写太重） |
| 已写好的文章要能公开 | 单对话摘要的**变体 B** | 组合版（会重写内容，破坏原文结构） |
| 多段对话合成一篇长文 | PROMPTS.md 的方向提示词 + 写作契约 | 单对话摘要（它假设只有一个对话） |
