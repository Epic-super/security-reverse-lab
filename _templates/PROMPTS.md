# PROMPTS · 让 AI 把你的破解/挖洞过程写成小白能看懂、能复现的文章

> **这个文件解决什么问题**
>
> 你手里有一堆对话记录：脱壳过程、协议还原、漏洞复现、靶场解题。
> 它们是**流水账**，不是**文章**。丢到 GitHub 上，别人看不懂，你也留不下经验。
>
> 这些提示词的作用：把「流水账」变成「**别人照着能跑一遍、你三个月后还能看懂**」的技术文章。
>
> **使用方法**：复制某个提示词 → 粘贴到你已有的那个对话里 → 它会基于你们的上下文继续写。
> 也可以在**新对话**里用，把原始素材（命令输出、截图描述、代码）一起粘进去。

## 0. 写作契约（最通用的底层规则，先贴这个）

> 这一段是所有提示词的公共部分。可以单独贴，也可以贴在 1/2/3 前面。

```text
你在帮我把一次真实的技术分析写成一篇**公开的技术文章**，读者是刚入门的小白。

## 写作契约（必须全部满足）

### 一、读者假设
- 读者会照着你的文章动手做，但**只懂基础命令行和一点编程**。
- 读者不知道你用的工具、不知道行业黑话、不知道你的思路为什么这么走。
- 所以：**任何一步都不能靠"你应该知道"来跳过。**

### 二、六条硬性要求

1. **先给结论，再讲过程**
   开头 3 行内说清：这是什么、结论是什么、读者看完能做什么。
   不要用"本文将带你……"开头，直接给结论。

2. **每个术语第一次出现时，必须用一句大白话解释**
   - 反例："这里用到了控制流平坦化混淆"
   - 正例："控制流平坦化（把 if/else 拆成一堆跳转，让反编译器的判断逻辑失效——这是常见的反分析手段）"
   - 英文术语首次出现保留原文并给中文：SROP（Signal Oriented Programming，信号导向编程）

3. **每个命令都要说清三件事**
   - **干什么用的**（一句话）
   - **在哪个目录/什么前提下**执行
   - **正常输出长什么样**（给出真实或示意输出）
   不要只贴一串命令让读者自己猜。

4. **原理必须讲原理，不能只讲操作**
   每一步都要回答"**这一步在计算机内部到底发生了什么**"。
   至少覆盖：
   - 涉及的文件格式/内存结构/协议报文的字段布局
   - 关键判断条件是怎么来的（是算法算的，还是硬编码的）
   - 为什么要这么做（作者的意图）

5. **必须可复现**
   - 列出全部前置条件：系统版本、工具及版本、样本/目标、依赖库
   - 命令从零开始写，包含准备环境的步骤
   - 每一步给出**预期输出**，让读者能判断自己是否走对
   - 标注哪些步骤依赖你自己的具体环境（用 `<!-- 读者注意 -->` 标出）

6. **不省略关键内容**
   - 不写"后面的过程类似"、不写"省略若干行"、不写"详见 XX"
   - 代码要给完整可运行版本，不是片段
   - 如果某一步确实复杂，允许分层：先主线，再展开细节

### 三、写作风格

- 句子短。一句话讲一件事。
- 主动语态："我们调用 X 函数"，不是"X 函数被调用"。
- 用**具体**替代**抽象**："缓冲区里前 4 字节是长度" 优于 "包含长度信息"。
- 表格能讲清楚的就用表格（字段布局、对比、输出对照）。
- 涉及字节、位、偏移、内存地址时，**明确标注是十进制还是十六进制**。
- 代码块标注语言；命令块标注 shell/batch。

### 四、章节骨架（除非我另有要求，按这个顺序）

```
# 标题
  一句话说明这篇文章解决什么问题

> **一句话结论**：……

## 0. TL;DR 速览
   - 是什么
   - 结论
   - 关键步骤（3–5 条，每条一行命令）

## 1. 背景与前置知识
   - 为什么要做这件事
   - 需要的最小知识背景（只讲必需的）

## 2. 环境准备
   - 系统 / 工具 / 依赖 / 目标
   - 每一步的验证方式

## 3. 原理讲解
   - 涉及的原理，用大白话 + 原理图/表格
   - 这一节独立可读，不依赖"做过的人"才懂

## 4. 实际操作
   - 分步骤，每步：目的 → 命令 → 预期输出 → 这步证明了什么
   - 关键判断点用「」标出来

## 5. 结果验证
   - 怎么确认真的成功了
   - 失败时的排查表

## 6. 踩过的坑
   - 现象 → 原因 → 解决
   - 这节最值钱，别省

## 7. 延伸与思考
   - 这个技术还能用在哪
   - 换个场景会怎么变

## 8. 复现清单
   - 逐步 checkbox，方便读者核对
```

### 五、输出方式

- **先输出完整文章**，不要先输出大纲问我确认。
- 写完之后，另起一段，用「」标出**文章的局限性**：哪里我需要你补充信息、哪里环境相关。
- 如果我给的信息不足以写某一节，**保留该节标题并写出你能确定的部分**，标注 `<!-- 需要补充：xxx -->`，不要编造。

### 六、禁止事项

- 不要编造没发生过的步骤、输出、参数、文件名、函数名。
- 不要用"很简单""很容易""众所周知"跳过解释。
- 不要在没给依据的地方下断言结论。
- 不要输出真实目标域名、真实 token/cookie/密码——统一用 `TARGET`、`example.com`、`TARGET_IP`、`<REDACTED>`。
```

## 1. 逆向分析文章（脱壳 / 静态分析 / 动态调试）

> 适合：脱壳过程、找关键函数、还原校验算法、还原加密算法、协议逆向。

```text
帮我把这次逆向分析写成一篇小白也能看懂、能照着复现的技术文章。

【本次分析的目标】
（例：分析 XXX 程序的 license 校验逻辑，还原算法）
（例：脱掉 XXX 的壳，还原原始代码）
（例：还原 XXX 的请求签名算法）

【目标样本信息】
- 文件名：
- 大小 / 格式：
- SHA256：
- 运行环境（要跑起来的话）：
（如果这些你不知道，问我，别编）

【我实际做的步骤】
（把对话里做过的操作、命令、观察到的现象贴过来，
  包括报错、试错、走过的弯路——这些是文章最值钱的部分）

【关键观察】
（你在哪个函数、哪个偏移、哪个字符串上确认了关键点？）

【已知结论】
（你自己已经得出的原理性结论，也贴上来）

═══════════════════════════════

除了上面那份「写作契约」，逆向类文章额外要求：

### A. 原理章节必须画清楚"东西在哪"
逆向文章最容易写成"我点了几下 IDA"。必须让读者知道**代码/数据在文件或内存里的物理位置**。

用表格讲清楚：

| 位置 | 含义 | 怎么找到的 |
|---|---|---|
| 文件偏移 0x1234 | ... | ... |
| 虚拟地址 0x401000 | ... | ... |
| RVA +0x2345 | ... | ... |

并解释这三种地址的区别（文件偏移 / 虚拟地址 / RVA），因为新手最常在这里迷路。

### B. 关键函数必须给"证据"
不要只说"关键函数是 sub_401000"。要写：
- 它被谁调用（交叉引用）
- 它的参数和返回值是什么（从反编译结果读出来）
- 你**怎么确定**它是关键函数（调用频率？参数特征？返回后进入了校验分支？）

### C. 算法还原要写"推导链"
如果还原出了算法，必须写出**你怎么一步步推到那个公式的**：

```
1. 观察：输入 "AAAA" → 输出 0x12345678
2. 猜：是不是某种哈希？
3. 验证：输入 "BBBB" → 观察输出变化 → 发现 4 个字节同时变了，排除单字节哈希
4. 拆函数：发现内部调用了 sub_X，其参数是前 8 字节
5. 确认：sub_X 是标准 AES 的 S-BOX 查表
6. 结论：(写出最终算法)
```

**"猜"和"验证"的过程不能删**——这是逆向文章和"贴代码"的分水岭。

### D. 动态调试部分必须给出"为什么在这里下断点"
新手最大的困惑是"为什么断在这个函数"。写清楚：
- 你观察到了什么现象（程序崩溃 / 界面变灰 / 网络请求发出）
- 你据此推断代码会在哪执行
- 你下了断点，看到了什么

### E. 命令必须给"最小可运行版本"
例如 Frida：

```bash
# 前置：设备已 root，frida-server 与客户端版本一致
pip install frida-tools
frida-ps -U                       # 确认能连上设备

# 完整脚本
frida -U -f com.example.app -l hook.js --no-pause
```

不要只给 `-l hook.js`，读者会卡在"hook.js 从哪来"。

### F. 必须说明工具的局限
常见坑要写出来：
- IDA 的 F5 反编译结果和真实逻辑不一致的情况
- 加壳样本在内存 dump 和静态反编译的差异
- 32 位和 64 位下 API 名称差异（`VirtualAlloc` vs `VirtualAllocEx`）
```

## 2. 漏洞分析文章（漏洞挖掘与复现）

> 适合：Web 漏洞、移动端漏洞、二进制漏洞、云上配置问题。

```text
帮我把这次漏洞分析写成一篇小白也能看懂、能照着复现的技术文章。

【漏洞类型】
（SQL 注入 / 越权 / XSS / SSRF / 反序列化 / 文件上传 / 命令注入 /
  客户端校验绕过 / 权限配置错误 / 其他）

【测试目标】
- 目标类型：（靶场 / 开源项目 / 自建环境 / 授权测试项目）
- 具体位置：
（真实域名一律写成 TARGET 或 example.com）

【我实际做的步骤】
（信息收集 → 定位 → 验证 → 利用链，把命令和请求贴过来）

【发现的响应差异】
（正常请求 vs 异常请求的对比，原始报文）

【影响面评估】
（能做什么、能拿到什么、影响多少用户）

【修复方式】
（对方给的补丁 / 你建议的修复，能给代码更好）

═══════════════════════════════

除了上面那份「写作契约」，漏洞类文章额外要求：

### A. 漏洞原理章节必须回答"为什么这里能注入"
不能只贴 payload。必须讲清楚根因：

```
根因：应用把用户输入直接拼进 SQL 语句，没有用参数化查询。

代码（示例）：
  query = "SELECT * FROM users WHERE id = " + req.query.id

于是输入 1 OR 1=1 变成：
  SELECT * FROM users WHERE id = 1 OR 1=1
```

同时讲清楚**为什么这一层没拦住**：
- 是 WAF 规则漏了这种写法？
- 是过滤只做了黑名单？
- 是编码解码顺序问题（先 URL 解码再过滤，但后面又解码一次）？

### B. 必须给"最小复现请求"
完整的原始 HTTP 报文，能直接粘进工具里跑：

```http
GET /api/user?id=1%20OR%201=1 HTTP/1.1
Host: TARGET
User-Agent: Mozilla/5.0
Authorization: Bearer <REDACTED>
Cookie: session=<REDACTED>
```

并给出**预期响应**和**实际响应**的差异（长度、状态码、关键字段）。

### C. 验证要"最小化 + 可控"
- 优先用**无害的证明**（布尔条件、延时、读取自己账号的数据）
- 不要一上来就脱库或拿高权限
- 写清楚"这一步证明了什么"，让读者理解证明力度

### D. 必须讲"怎么找到的"
这是挖洞文章最有价值的部分。**只讲漏洞不讲发现过程的文章，读者学不到东西。**

按攻击面分阶段写，每阶段给出：
- 目的
- 工具/命令
- 输出里看什么（关键特征）
- 判断依据

例如信息收集：
```
阶段 1：子域枚举
  命令：subfinder -d TARGET -all
  输出特征：注意 dev.*、staging.*、api.* 这些前缀
  判断：这些子域往往没上 WAF

阶段 2：端点枚举
  命令：ffuf -u https://TARGET/FUZZ -w wordlist.txt -mc 200,204,301
  输出特征：注意长度明显大于 404 基线的响应
```

### E. 影响面与严重度要给出理由
说明为什么评这个等级（CVSS 向量要写出来），以及**哪些情况下不成立**（比如需要特定前置条件）。

### F. 修复建议必须可落地
给代码级别或配置级别的改法，不要写"建议做输入校验"这种空话。写清：
- 改哪里
- 改成什么
- 为什么这个改法能堵住（回到第 A 节的根因）

### G. 脱敏检查（结尾必须有）
- [ ] 域名 → TARGET / example.com
- [ ] Token / Cookie / Key → <REDACTED>
- [ ] 真实用户数据 → 已删除或替换
- [ ] 漏洞未修复前不公开细节（如果你打算提交赏金）
```

## 3. writeup 复盘（一次完整的解题或提交流）

> 适合：Vulnhub/HTB 靶场、HackerOne/Bugcrowd 报告、一次完整提交流。

```text
帮我把这次完整的解题/提交流写成一篇复盘文章。

【这次的目标】
（靶场名 / 项目名 / 平台）

【最终成果】
（flag / 漏洞赏金金额 / CVSS 评分 / 排名）

【我的完整路径】
（从信息收集到拿到结果的每一步，按时间顺序）

【关键转折点】
（哪一步让我意识到方向对了，或者走错了又绕回来）

═══════════════════════════════

除了上面那份「写作契约」，writeup 额外要求：

### A. 必须有一条清晰的"攻击路径总览"
放在最前面，让读者一眼看到全貌：

```
枚举 (80/22) → Web 弱口令 (80) → 反弹 shell (4444) → 本地提权 (john) → root → flag
```

每个箭头下面标注**用的什么技术**。

### B. 必须诚实写"走过的弯路"
这是 writeup 最有价值的部分，也是最常被省略的。

用表格：
| 我先试了什么 | 结果 | 为什么错了 |
|---|---|---|
| 用 dirsearch 爆破 | 全 403 | 站点其实没挂目录索引，应该先看 JS |

**读者最常踩的坑，往往就是你踩过的坑。**

### C. 每个提权/绕过都要讲"原理"
不要只给命令。讲清楚：
- 提权利用的是哪个系统特性（SUID / sudo 配置错误 / 可写 service 文件 / 计划任务权限）
- 这个特性本来是干什么用的
- 为什么在这个环境下能被滥用

### D. 结尾必须有"复现清单"
逐步 checkbox + 预期现象，让读者能一格一格核对：

- [ ] 目标机器已启动，IP 为 TARGET_IP
- [ ] `nmap -sV -p- TARGET_IP` 看到 22/80 开放
- [ ] 目录爆破得到 /admin/，返回 302 跳转到 login
- [ ] ...（每格都要写预期现象）

### E. 结尾必须有"我学到了什么"和"下次会怎么做"
不是感想，是**具体的做法改进**：

- 这次花了 3 小时才做端口全扫，下次应该先 `nmap -p- --min-rate 5000` 提速
- 这次在 SQLi 上耗了很久，其实响应里就有明显的时间差，应该早点用时间盲注确认

### F. 如果是漏洞提交流，额外加一节
- 报告质量自查：可复现性 / 影响面论证 / 修复建议是否可落地
- 沟通记录：对方问了什么、你怎么答的（这决定了赏金谈判结果）
- 收获：下次写报告要改进的地方
```

## 5. 自检清单（写完贴这个，让 AI 挑毛病）

```text
请以严格的技术审稿人身份检查下面这篇文章，逐条给结论：

【检查项】
1. 有没有从"我做了什么"写成"读者能跟着做"？——逐段判断哪些段落只对作者有意义
2. 每个术语第一次出现的地方，有没有大白话解释？列出所有缺失的
3. 每个命令，是否三件套齐全（干什么用的 / 在哪执行 / 预期输出）？列出缺失的
4. 原理章节是否独立可读？有没有依赖"读者也做过"才懂的地方？

## 6. 一条完整的用法示例

假设你在某个对话里刚脱完一个壳，想把它写成文章：

**第一步**（在原对话里）：贴「1. 逆向分析文章」提示词

**第二步**（新对话里，验证）：贴「5. 自检清单」提示词 + 文章正文

**第三步**（修补）：把审稿意见发回原对话，让它按意见改

**第四步**（归档）：存到仓库对应目录：

```
01-reverse/04-unpack/<壳名>/
├── README.md       ← 文章正文
├── notes.md        ← 踩坑表、试错记录
└── artifacts/      ← 脚本、样本哈希
```

## 7. 通用原则（为什么这样设计）

| 原则 | 原因 |
|---|---|
| 先结论后过程 | 读者判断"这篇对我有没有用"只需要 3 秒 |
| 术语首次必解释 | 小白卡住的地方 90% 是术语 |
| 命令三件套 | 缺预期输出，读者无法判断自己是否走对 |
| 原理必须独立可读 | 原理是唯一能**迁移**到下个 case 的东西 |
| 必须写弯路 | 弯路是读者真正的痛点，教程不会告诉你 |
| 禁止编造 | 一次编造就会让整篇失去可信度，且读者会照着踩坑 |
| 脱敏用占位符 | 保护自己 + 让文章可公开 |

> **一句话**：**教程告诉你"怎么做"，文章要告诉你"为什么这样做，以及我为什么这么判断"。**
> 后者才是有价值的部分，也是能沉淀成你自己能力的东西。
